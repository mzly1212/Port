# 港口复杂场景感知过滤与轨迹平滑引擎

![Python](https://img.shields.io/badge/Python-3.8+-blue.svg)
![Status](https://img.shields.io/badge/Status-生产部署中-green.svg)

## 📖 项目简介

在真实的港口/路侧部署环境中，融合感知设备（毫米波雷达 + 摄像头）输出的原始数据往往伴随着高频跳动、同车多点分裂、长拖挂车严重遮挡断联、ID 频繁跳变、雷达前后混淆（车头 180° 翻转）等痛点。本引擎作为承上启下的**中间件**，核心职责是：

> **接收上游感知设备高频（10Hz）且伴随噪点的原始数据，在底层进行物理坐标清洗、跳变 ID 缝合、幽灵噪点剔除、固定设施位姿钉锚以及盲区轨迹推演，最终将平滑、稳定的车辆数据与透传业务属性，按照 ITC V1.20 协议组包推送给下游大屏前端。**

针对港口复杂路况（海一路双向对向车道错乱、T 字路口急转、右侧边界入场旋转、堆场车道严禁逆行、舱盖板密集排布等）进行了大量定制化的状态机防错与几何拓扑优化。

### 数据流总览

                                    │                                      │
┌─────────────────┐   UDP :10011    │  main.py        算法版 (原版)          │
│  第三方数据源      │ ───────────────> │  refactor/      重构版 (主力开发)      │
└─────────────────┘  (固定设施专用)    │  main_raw.py    纯透传对比版           │
                                    │                                      │
                                    │  selectors 单线程多路复用收包           │
                                    │         │                            │
                                    │         ▼                            │
                                    │  input_adapter  8B头+Protobuf 解析    │
                                    │         │                            │
                                    │         ▼                            │
                                    │  LaneQueueTracker 六阶段流水线         │
                                    │  (缝合/去重/推演/设施锚定/航向仲裁)      │
                                    │         │                            │
                                    │         ▼                            │
                                    │  output_adapter ITC V1.20 组包        │
                                    │         │                            │
                                    └─────────┼──────────────────────────────┘
                                              │ TCP :7098 (断线自动重连)
                                              ▼
                                    ┌─────────────────┐
                                    │   前端大屏/ITC    │
                                    └─────────────────┘

### 双数据源设计

| 数据源 | 端口 | 频率 | 内容 | 说明 |
|---|---|---|---|---|
| 星云互联 | UDP 10001 | 10Hz | 移动车辆 + 噪点 | 主数据源 |
| 第三方 | UDP 10011 | 低频 | **固定设施（舱盖板等）专用** | 报文格式与星云完全相同（8字节头 + Protobuf），我们作服务端监听，对方推送 |

两路数据通过 `selectors` **单线程多路复用**串行喂引擎——跟踪器的 `active_vehicles` 等共享状态无锁，多线程并发处理会有线程安全问题，事件循环结构上杜绝竞态。

### 三个入口版本

| 入口 | 用途 | 算法处理 | 多源合并方式 |
|---|---|---|---|
| `main.py` | 原版算法部署 | ✅ | 交错喂帧（跟踪器天然合并） |
| `refactor/main.py` | **重构版（主力开发）** | ✅ | 同上 |
| `main_raw.py` | 纯透传对比基准 | ❌ 原样透传 | `SourceMerger` 帧合并 |

⚠️ 三个入口都绑定 10001 + 10011 双端口，**同一台机器同时只能运行一个**，否则第二个启动会报端口占用。

- 算法版：跟踪器内目标跨帧存活，每帧输出含全部目标，天然"合并"两路数据。
- 透传版：无跟踪状态，若每帧只透传单源目标，前端会以两源交替频率闪烁——因此用 `SourceMerger` 缓存各源最近一帧目标，收到任意源新帧时合并所有新鲜源（1 秒超时剔除）合成一帧下发。

## 🔬 核心算法机制

### 1. 六阶段处理流水线（refactor 版架构）

每帧按序执行，各阶段职责单一：

```
Stage 1  输入门卫     入场航向初始化 / 设施身份防劫持 / 设施低频刷新节流
Stage 2  ID 关联     海一路仲裁 / 预滤波 / 车道匹配 / 防劫持护盾 / 2D 缝合
Stage 3  测量应用     同车道 / 变道确认 / 离道上轨
Stage 4  物理推演     离道去重 / 490 拦截 / 在轨去重 / 断联推演 / 追击收敛
Stage 5  生命周期     双轨超时清理
Stage 6  输出合成     坐标融合 / 航向仲裁 / 输出平滑
```

### 2. 方向滞回状态机（根治车头 180° 翻转）

车头来回翻转的根源是测速噪声导致符号抖动。解法：

- **死区**（`DIR_DEADZONE=0.8m/s`）：低速时速度符号视为噪声，不参与方向判定
- **连续确认**（`DIR_CONFIRM_N=5`）：方向翻转需连续 5 个有效采样确认（约 0.5 秒）
- **测速历史永不清空**：ID 跳变缝合时保留全部测速历史与方向状态——若每次缝合都清历史，方向状态机永远无法确认，车头会退化到雷达航向兜底而来回翻转/倒行（生产事故教训）
- **边缘抖动豁免**（`REENTRY_BLIP_MS=1000`）：离道后 1 秒内重回原车道视为车道边缘位置噪声，不重置方向状态

### 3. 航向翻转标记与豁免（前后混淆签名）

雷达前后混淆（车头 180° 报反）的专属签名是**单帧航向跳变 >120°**（`HEADING_FLIP_MARK`）——真实转弯的滤波滞后每帧仅 ~36°，物理上不可能触发。

- 检测到翻转标记后 4 秒内（`HEADING_FLIP_TRUST_MS`）该车雷达航向不可信，**缝合/去重的航向否决对其豁免**，回到纯几何仲裁
- 这解决了"航向否决死锁"：没有豁免时，前后混淆相位的车永远无法关联更新，每帧分裂出新目标

### 4. 全域 2D 物理缝合（新 ID 认领老车）

ID 跳变的三种场景坍缩为同一套缝合逻辑：

- **场景 1 断联重连**：断联超过 `SUTURE_GAP_MS=100ms`，新 ID 出现在 `30 + v·gap`（封顶 70m）范围内
- **场景 2 极近距离分裂**：新 ID 距老目标 < `SUTURE_SPLIT_DIST=18m` 强行认领
- **航向否决**：航向近乎正对（>150°，对向车签名）拒绝缝合。⚠ 历史教训：90°~120° 否决曾误杀感知交界处同车双报（航向差可达 120°+），已回退
- **缝合基线统一**：缝合点立即用老车的滤波器重新处理观测并重新匹配车道，测量基线全程一致，消除缝合瞬间的 S 跳变
- **重连动画**：同车道重连位置跳变 >2m 时启动输出过渡动画（复用变道动画机制），消除画面瞬移

### 5. 固定设施保护（舱盖板/候工亭，不去重只固定位姿）

固定设施（`itc_sub_type=13` 候工亭/锁销框、`14` 舱盖板）的处理原则与车辆完全相反——**设施静止，不存在缝合/去重需求，只固定位姿**：

| 防线 | 机制 |
|---|---|
| 去重豁免 | 在轨/离道去重均跳过设施目标，密集舱盖板（间距 < 18m）不会被互相吞并 |
| 缝合隔离 | 设施点不认领任何 ID（车/设施都不认领），每个设施独立持有 ID |
| ID 跳变兼容 | 未知类型（99）且 ≤5m 的点仍可认领设施（设备偶发把设施报成未知类型） |
| **位置锚定** | 10 帧中位数确认锚点 → 抖动静区（≤0.5m 钉死）→ 误绑定阈值（>3m 拒绝）→ 持续偏移 15 秒才重锚定（兼容吊装搬运） |
| **低频刷新节流** | 第三方设施数据每分钟只刷新一次位姿（`FACILITY_REFRESH_MS=60000`），窗口内量测仅作心跳续命，图标完全静止 |
| 超时保护 | 存活期 70 秒（> 刷新周期），第三方偶尔丢一拍不闪图标 |

### 6. 堆场车道航向严格锁定

堆场内车道（`SPECIAL_LINES['DUICHANG']`，10 条）上的车辆**物理上不可能逆行**——测速噪声误判反向、雷达前后混淆等一切"逆行"迹象都是感知错误：

- 输出层最高优先级分支：堆场车道上的车头**恒锁车道正向**
- 只锁输出层，不动方向状态机：`drive_direction` 仍正常参与测速、推演、缝合等内部逻辑，不破坏既有行为

### 7. 断联推演与无缝追击（Chase & Replace）

车辆被遮挡/驶出感知范围后：

- **指数速度衰减**（`PRED_SPEED_DECAY_TAU=3.0s`）：3 秒后速度剩 37%，8 秒后剩 7%，衰减到 0.3m/s 以下视为静止——静止车盲区零漂移，运动车按物理可达距离漂移
- **IDM 跟车减速**：前方 15m 有车时以 2m/s² 减速，避免盲区推演穿透前车
- **追击替换**：车辆恢复检测后不暴力瞬移，以弹性追击速度（最大 3m/s 差值）让推演车平滑追上真实雷达点后完成替换
- **存活期**：在轨车 8 秒 / 离道车 2.5 秒，超时清理

### 8. 离道车航向物理约束（三重防线）

不在车道上的车没有车道航向基准，容易因感知噪点大幅偏转：

1. **噪点门限**：单帧航向突变 >45°（`HEADING_NOISE_JUMP`）视为噪点拒绝
2. **运动矢量纠正**：雷达航向杂乱且与 3 秒轨迹运动矢量矛盾 >90° 时，用运动矢量纠正
3. **限转速输出**：输出航向最大 45°/s（`HEADING_MAX_RATE`），任何来源的突变都被渲染为平滑转动

另有：静止目标航向冻结（感知突翻 180° 输出不动）、倒车豁免（真实倒车不被错误翻转）。

### 9. 海一路特化（双向车道会车错乱）

海一路是双向单车道，单侧雷达极易产生对向吸附：

- **向量夹角仲裁**：入轨边界（距 506 车道 2.5~8m）持续线性拟合轨迹向量，逼近 2.5m 时与双向车道走向做最小夹角比对，一票否决制裁决入轨车道
- **会车防劫持护盾**：老车道中心却瞬跳对向车道（横向偏移 <1m）或航向突变 >90° 且 dt <1s 的量测直接丢弃
- **490 横穿离场拦截**：滤波横向偏移 >2m 判为横穿离场

### 10. 车型投票锁定

对 `itc_sub_type` 执行置信度加权投票，防止图标在卡车/客车/未知间闪烁：

- 票数时间衰减（`TYPE_DECAY=0.98`，半衰期约 3.4 秒）
- 双门槛锁定：占比 >60% 且观测 ≥8 帧（设施更严格：85% + 10 帧）
- 移动目标报设施类型拒绝锁定（静止证据校验）
- 已锁定类型的纠正门槛 80%，防止偶发误报翻转

### 11. 变道平滑

- **确认机制**：连续 5 帧匹配同一新车道且偏离 >1m 才确认变道（防边缘抖动误判）
- **余弦缓动动画**：2000ms `Cosine Ease-in-out` 横向过渡动画，变道瞬间无跳变
- **逆行保持**：借道超车/逆行时动态保持车头物理真实朝向，不因匹配对向车道 180° 翻转

## 🌐 网络与连接管理

### 输入（UDP，双源监听）

```python
UDP_NEBULALINK_IP = "0.0.0.0"
UDP_NEBULALINK_PORT = 10001     # 星云互联
ENABLE_THIRDPARTY_INPUT = True  # 第三方数据源开关
UDP_THIRDPARTY_PORT = 10011     # 第三方（固定设施专用）
```

报文格式（两源相同）：`4B Magic(0xdadbdcdc) + 1B 数据类型(0x01) + 1B 感知类型(0x07) + 2B 长度(大端) + Protobuf PerceptronSet`

### 输出（TCP 多目标推送，断线自动重连）

```python
# 处理后的数据推送给列表中的所有前端, 每个目标独立连接/独立重连
WEB_TARGETS = [
    ("10.28.49.196", 7098),
    # ("192.168.1.100", 7098),   # 新增前端: 在此追加 (ip, port)
]
WEB_SEND_TIMEOUT = 2.0          # 发送/连接超时(秒)
WEB_RECONNECT_INTERVAL = 5.0    # 断线重连尝试间隔(秒)
# 未配置 WEB_TARGETS 时回退到旧单目标 TCP_WEB_IP / TCP_WEB_PORT
```

多目标推送（`web_sender.py` 的 `WebSender`，三个入口共用）：

| 场景 | 行为 |
|---|---|
| 启动时某前端未就绪 | 该目标单次尝试失败后进入周期重连，**不阻塞程序启动与其他目标** |
| 某前端断开（Broken pipe） | 仅关闭该目标的死连接，其余目标照常收数；每 5 秒重连该目标 |
| **半死前端**（TCP 活着但应用不读） | `sendall` 2 秒超时即断开重建——防主循环冻结导致 UDP 缓冲撑爆静默丢包（历史生产事故模式） |

> TCP 断连检测天然滞后一帧（首帧进本地缓冲仍"成功"，RST 传回后才报错），丢 1 帧可接受。

### 日志与落盘

| 开关 | 输出 | 用途 |
|---|---|---|
| （默认开启） | `logs/perception_server.log` | 运行日志（50MB 轮转 ×5） |
| `SAVE_REPLAY_DATA` | `logs/replay_data.jsonl` | 原始+修复后双流落盘，供回放对比 |
| `SAVE_THIRDPARTY_RAW` | `logs/thirdparty_raw.bin` | 第三方原始二进制报文落盘（含坏包留痕） |

第三方落盘格式：`[8B 接收时刻 epoch ms][4B 包长][原始报文]`，可直接喂 `parse_udp_packet` 回放。注意无自动轮转（10Hz × ~1KB ≈ 36MB/小时），长期开启需手工转存。

### 调优红线（历史教训，勿重蹈）

1. **缝合距离阈值勿收到 12m**——会导致感知边界分裂车增多（已回退至 18m）
2. **航向否决勿放宽到 90°~120° 全车道**——会阻断感知交界处合法缝合（已回退至仅 >150°）
3. **缝合时勿清空测速历史（hard_reset_s）**——方向状态机永远无法确认，车头来回翻转/倒行（已回退）
4. **改 `FACILITY_REFRESH_MS` 时保持 `FACILITY_TIMEOUT_MS` 大于它**
5. **方向状态机死区、单向棘轮、航向兜底翻转都依赖 signed_v 符号稳定性**——收紧死区会让棘轮更频繁反转
